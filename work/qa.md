## 阶段自测记录

### A. 数据

- 重写 `work/fetch-anime-data.mjs`：AniList 批量分页（`POPULARITY_DESC`，TV / Movie / ONA，≥2005）
  + Bangumi（`api.bgm.tv/v0/search/subjects`，带文档要求的 User-Agent，间隔 ≥1.1 秒）补中文名与中文简介；
- 请求层：节流 ≥1.1s、单次 20s 超时、429 / 403 / 5xx 按 `Retry-After` 或指数退避重试（最多 4 次）、
  失败结果缓存 10 分钟、成功结果缓存 14 天；
- 健壮性：条数 < 300 判定抓取不完整，保留旧 JSON 不覆盖（小样本试跑时实测触发过该保护）；
  热门列表 < 10 条同样保留旧文件；
- 运行实况：AniList 共 12 页批量请求；Bangumi 539 次查询命中 476 条，期间 1 次 `fetch failed` 自动重试成功；
  首次完整抓取约 9 分钟，重跑全命中缓存只需数秒；
- 数据源优先级：AniList（主）→ Bangumi（中文）→ Jikan（可选回退；本次运行时 Jikan 持续 504，故未使用，报告如实记录）。

### 过程中发现并修复的两个问题

1. **静态资源缓存混用**：部署后一度出现「新 HTML + 旧 JS」的混合状态（首页只渲染出骨架屏、
   年份轴与统计为空）。原因是 CDN / 浏览器仍缓存着同名的旧 `*.js`。
   已修复：四个页面的 CSS / JS 引用统一加上版本号（`?v=20260914b`），以后每次改动资源时同步递增版本号即可。
2. **数据 JSON 请求可能长时间挂起**：个别网络下 `fetch('data/anime.json')` 会一直不返回，
   页面停在骨架屏（无报错、无超时）。已修复：`data.js` 的 JSON 请求加 9 秒 `AbortSignal.timeout`，
   超时或失败会自动改用同内容的 `data/anime.js` 兜底；修复后线上复检显示
   「数据来源：data/anime.json」正常渲染 539 部。

### 本轮发现并修复的问题

1. **「加载更多」按钮一直可见但点了没用**：`style.css` 里 `.btn { display: inline-flex }` 覆盖了浏览器默认的
   `[hidden] { display: none }`，所以按钮的 `hidden` 属性不生效——没有更多时也显示，点了自然没反应。
   已修复：样式表加 `[hidden] { display: none !important; }`，并按「已显示 < 过滤后总数」控制显隐，
   文案改为「显示更多（还剩 X 部）」，一批装得下就完全隐藏。
2. **接近底部不会自动加载**：原实现只在渲染后检查一次，滚动时没有触发点。已修复：改为**滚动监听 + IntersectionObserver** 双通道，
   进入列表底部 520px 内自动加载下一批（实测 96 → 144 → 192 部），按钮只作后备。

1. **某公司部数 = 精选库命中部数**，不是该公司的全部作品；站点与 README 都已写明。
2. **热门快照不会自动更新**，需要重新跑 `node work/fetch-anime-data.mjs --only=trending`。
3. 分类 / 年份 / 季度的分面数量按「当前其它条件不变」实时计算（前端 539 条内即时完成），
   公司分面数量在首次打开公司下拉时计算一次并缓存，切换筛选后失效重算。
4. 站点仍不提供播放、不含下载入口；本轮没有新增任何播放源、统计脚本或账号系统。
